# Seens Radio — How the AI DJ & Recommendation System Works

This document traces the full end-to-end flow from a user request (or automatic trigger) to audio playing in the queue, with a focus on how the AI DJ, track resolver, and reranker work together.

---

## System Overview

```
User / Scheduler
      │
      ▼
  router.js  ← handleInput(message, triggerType)
      │
      ├─ 1. Build system prompt (taste + context + history)
      │
      ├─ 2. AI DJ call (Claude / Codex)
      │         └─ returns { say, play[], candidates[], playIntent, ... }
      │
      ├─ 3. [Optional] Plugin two-pass (podcasts, news, etc.)
      │
      ├─ 4. Parallel:
      │         ├─ resolveTracksOrdered()   → find audio URLs (Spotify/YT/Apple)
      │         ├─ synthesize(say)          → TTS mp3 for DJ voice
      │         └─ rerank(play+candidates)  → seens-reranker subprocess
      │
      ├─ 5. Apply reranker order, lock play[0]
      │
      ├─ 6. Enqueue resolved tracks + broadcast to UI
      │
      └─ 7. Feedback loop: like/skip/replay → taste centroids
```

---

## Step 1 — Triggers

The system can be activated by three sources:

| Source | Trigger type | When |
|---|---|---|
| User message / Tune In | `user-chat` | User types a request or clicks Tune In |
| Queue runs low (< 2 tracks) | `auto-refill` | Automatically when queue empties |
| Scheduled cron jobs | `morning-energy`, `mood-check`, etc. | Pre-defined times (7 AM weekday, 6:30 PM, midnight, …) |

All three paths call `handleInput(message, triggerType)` in `src/router.js`.

---

## Step 2 — System Prompt Assembly (`src/context.js`)

Before calling the AI, `buildSystemPrompt()` assembles a rich context block:

```
DJ Persona (dj-persona.md)
├─ Role, output format rules, curation philosophy, hard constraints

User Taste (taste.md)
├─ Spotify top artists / listening rank, liked artists, disliked artists

User Routines (routines.md)
├─ Daily schedule, energy preferences by time of day

Session History
├─ Recently played tracks (dedup list)
├─ Hard-block list (songs played this session — ABSOLUTE NO REPEAT)
├─ Recent skips and feedback signals

Music Library (playlists.json)
├─ Songs from Spotify, Apple Music, YouTube — used as candidates
├─ Discoverable tracks (deeper cuts the user hasn't heard yet)

Environment
├─ Current time, day, season
├─ Weather (WMO code from Open-Meteo)
├─ Calendar events (Google / Microsoft) — upcoming gym, meeting, etc.
├─ Location
├─ Session mood seed (random adjective fixed per session for tonal consistency)

Temporal Listening Profile
├─ Generated by getTemporalPlaysProfile() — what the user typically plays
│   at this time of day/week (e.g. "weekday mornings: lo-fi, ambient")
│   Injected as text so the language model understands time-of-day routines.
```

This context is reassembled on every call — it always reflects the latest state.

---

## Step 3 — AI DJ Response

The AI (Claude or Codex) receives the system prompt and user message, and must return a single JSON object:

```json
{
  "say": "Sedona by Houndmouth — written in one afternoon…",
  "play": [
    { "title": "Sedona", "artist": "Houndmouth", "source": "spotify" },
    { "title": "Ends of the Earth", "artist": "Lord Huron", "source": "any" },
    "... 6–8 more songs"
  ],
  "candidates": [
    { "title": "Stolen Dance", "artist": "Milky Chance", "source": "any" },
    "... 10–15 additional songs the DJ doesn't speak about"
  ],
  "playIntent": "now | next | end",
  "reason": "internal reasoning not spoken aloud",
  "segue": "teaser for the next track transition"
}
```

**`play`** (8–10 songs): The DJ's curated list. `play[0]` is the song the DJ explicitly names in `say` — it is announced and **cannot be displaced**.

**`candidates`** (10–15 songs): Extra nominations the DJ does not speak about. They expand the scoring pool without affecting the intro. The reranker scores all `play + candidates` together (~25 songs) and selects the best subset.

**`playIntent`** controls when tracks queue:
- `"now"` → interrupt current music immediately
- `"next"` → hold DJ intro until end of current song
- `"end"` → silent add to queue (auto-refills and session starts)

### Plugin Two-Pass

When the AI detects a request for external content (podcasts, news), it returns a `pluginCall` in pass 1. The router fetches the data, then calls the AI again (pass 2) with the result. Pass 2 produces the final `say` and `pluginAction` with the actual audio URL.

## Step 4 — Parallel: Resolve + TTS + Rerank

All three operations run in parallel to minimize latency:

```
Promise.allSettled([
  resolveTracksOrdered(djResponse.play),
  synthesize(djResponse.say),
  rerank([...play, ...candidates]),
])
```

### 4a. Track Resolution (`music/resolver.js`)

For each song in `play`, the resolver finds a playable audio URL:

```
For each track:
  1. Try Spotify (URI lookup if available, otherwise search)
  2. Try Apple Music (MusicKit search)
  3. Fallback: YouTube search via yt-dlp
     → "Song Title Artist Name official audio"
  → Returns: { title, artist, videoId, streamUrl, resolvedTitle, ... }
```

Resolution runs in order to preserve DJ-intended sequence. Unresolved tracks are included with `streamUrl: null` — the frontend skips them automatically.

### 4b. TTS (`src/tts.js`)

The DJ's `say` text is synthesized to an mp3. This runs in parallel with resolution so audio is ready when the first song starts. TTS is skipped for auto-refills (transition mechanism handles the intro separately).

### 4c. Reranker (`src/reranker.js` → `seens-reranker/`)

The full `play + candidates` pool (~25 songs) is sent to the reranker subprocess over JSON-RPC stdin/stdout.

---

## Step 5 — The Reranker Pipeline

The reranker (`seens-reranker/`) is a Python subprocess that runs ML models locally.

### 5a. Subprocess Communication

```
seens-radio (Node.js)
    │  stdin:  { "id": "1", "method": "rerank", "params": { candidates, context, top_k } }
    │  stdout: { "id": "1", "result": { "songs": [...ranked...] } }
    ▼
subprocess_main.py → dispatch() → pipeline.py:rerank()
```

seens-radio first fetches real lyrics for all candidates via LRCLib (batch, 5s timeout). Better lyrics → richer BGE text embeddings → more accurate reranking.

### 5b. Embedding

For each song in the pool:

| Encoder | Model | Encodes | Dimension |
|---|---|---|---|
| MERT | m-a-p/MERT-v1-95M | Instruments, timbre, structure | 768 |
| CLAP | laion/larger_clap_general | Mood, energy, vibe | 1024 |
| BGE-M3 | BAAI/bge-m3 | Lyrics, emotional theme | 1024 |

BGE is batch-encoded first (one forward pass for all songs without cached BGE). MERT and CLAP are loaded concurrently per song. All embeddings are cached in SQLite — songs only pay the encoding cost once.

### 5c. Taste Vectors

The reranker loads up to 9 taste signals from the DB:

| Signal | Source |
|---|---|
| `taste_mert/clap/bge` | Global taste centroid — mean of all liked song embeddings |
| `taste_temporal_mert/clap/bge` | Time-bucket centroid for the current slot (e.g. `weekday_morning`) |
| `skip_mert/clap/bge` | Skip centroid — mean of all skipped song embeddings |

Taste vectors are `None` for new users and are added to the signal set only when enough data exists — the model degrades gracefully.

### 5d. Attention Fusion Model (`reranker/attention_fusion.py`)

```
Context (time, weather, mood, energy)
    └─ ContextEncoder → query (B, 256)

Signals (up to 10 when all taste available):
    mert (768), clap (1024), bge (1024),
    taste_mert, taste_clap, taste_bge,
    taste_temporal_mert, taste_temporal_clap, taste_temporal_bge,
    context (256)
    └─ SignalProjection: each → Linear → normalize → (B, 256)

DotProductAttentionFusion:
    sim   = query · keys.T / sqrt(256)   → (B, n_signals)
    attn  = softmax(sim)                 → interpretable weights
    fused = attn @ keys                  → (B, 256)

score_head: Linear(256→128) → GELU → Linear(128→1)
    └─ score per candidate
```

The attention weights are interpretable — they show which signal drove each ranking decision (e.g. high `taste_temporal_clap` weight means the model prioritized mood/energy match to the current time-of-day routine).

### 5e. Skip Penalty (post-scoring)

After the attention model scores all candidates, a skip penalty is applied:

```
For each model (mert, clap, bge):
  sim = cosine_similarity(candidate_embedding, skip_centroid)
  score -= max(0, sim) × 0.25
```

Songs acoustically or lyrically similar to what the user skipped are softly discouraged. Requires ≥ 2 skipped songs with embeddings to activate.

### 5f. Return

Songs are sorted by final score descending. The result includes `reranker_score` and `attention_weights` per song.

## Step 6 — Apply Reranker Order + Enqueue

Back in `router.js`:

```
play[0] is LOCKED — the DJ announced it in say, it stays first.
Reranker result fills play[1:] + candidates → sorted by score.
Final playlist = [play[0], ...reranker_top_N_excluding_play0]
```

Log output:
```
[Router:user-chat] reranker done — AI order: "Little Talks" → "Anna Sun" → ...
[Router:user-chat] reranker done — top: "Sedona" by Houndmouth | reranked: "Sedona" → ...
```

The resolved tracks are then re-sorted to match the reranked order and enqueued. The DJ voice (TTS) and `firstTrack` are broadcast to the UI.

---

## Step 7 — Feedback Loop

Every user action feeds back into the reranker's taste model:

```
User skips track
    └─ routes/feedback.js → sendFeedback(track, "skip")
           └─ reranker: record_feedback() → feedback table
           └─ update_taste_centroid():
                 skip_centroid = mean(skip embeddings) → save to DB

User likes track
    └─ routes/feedback.js → sendFeedback(track, "like")
           └─ update_taste_centroid():
                 global_centroid = mean(liked embeddings) → save
                 temporal_centroid[current_bucket] = mean(liked in bucket) → save

Track plays to end (no skip)
    └─ routes/next.js → sendFeedback(track, "replay")
           └─ same as like — natural finish = positive signal
```

### Time Buckets (10 total)

The temporal taste system learns what the user prefers at each time slot:

```
weekday_morning    Mon–Fri  06:00–09:59
weekday_midday     Mon–Fri  10:00–13:59
weekday_afternoon  Mon–Fri  14:00–17:59
weekday_evening    Mon–Fri  18:00–21:59
weekday_night      Mon–Fri  22:00–05:59
weekend_*          (same slots, Sat–Sun)
```

After each like/replay, `update_temporal_taste_centroids()` groups all liked songs by their play timestamp, computes a normalized mean embedding per bucket, and saves it. The next rerank uses the centroid for the current wall-clock bucket.

---

## Step 8 — Similar Song Search

When the user says "play something similar" / "more like this" / "same vibe":

```
1. router.js detects intent regex: /similar|like this|same vibe|more like|sounds like/i

2. findSimilar(activeSong, limit=20):
   └─ reranker: find_similar method
        ├─ get_embedding(song_id, "clap")   ← mood/vibe query vector
        │   (fallback: "mert" if CLAP missing)
        ├─ knn_search("clap", query_vec, k=60)  ← sqlite-vec KNN
        ├─ load song metadata for top candidates
        └─ rerank(candidates, context_kwargs)   ← full pipeline

3. Results merged with DJ's pool:
   └─ rerankerPool = [...djPool, ...simFresh]   ← up to 40 songs total
   └─ full rerank on combined pool
   └─ user hears acoustically similar songs, filtered by taste
```

## Auto-Refill

When the queue drops below 2 tracks, `routes/next.js` fires `handleInput(prompt, 'auto-refill')`:

```
prompt: "Based on my recent listening history (Artist A, Artist B, ...),
         queue 4 more tracks I'll enjoy. Vary the mood and avoid repeating
         what was just played."
```

Auto-refills use `playIntent: "end"` (no interruption) and skip TTS for the intro (the transition mechanism handles voice segues when the track is nearly done).

A 45-second startup grace prevents auto-refill from racing with the user's initial "Tune In" request.

---

## Reranker Subprocess Lifecycle

```
enableReranker()
    └─ spawn python subprocess_main.py
    └─ _warmup(): health check (waits up to 15 min for HuggingFace download)

On crash (SIGSEGV etc.):
    └─ exit handler detects signal != null
    └─ auto-restart after 5s if reranker still enabled

disableReranker()
    └─ sends "shutdown" RPC, then SIGTERM
    └─ clears restart timer
```

The subprocess uses a PID lockfile to kill stale instances on startup, preventing "database is locked" errors when the app restarts mid-inference.
